# 0004 · 状态日志只留两天, 其余逐日 gzip 归档

## 状态

已采纳 (2026-10-25)

## 背景与问题

状态日志原先"按天分片, 7 天后打包成 ZIP"。实际实现与这个描述有四处偏离, 且归档时机几乎不可达:

1. **归档只在轮询的跨天分支里执行**, 而 `lastPollDate` 初值为空串, 所以启动后的第一次轮询不会触发; 此后只有进程**活着跨过午夜**才可能归档。每天重启的机器人一次也不会归档, 文件无限堆积。未配置 Steam API Key 时轮询根本不启动, 归档同样不发生。
2. **保留规则是"最新 7 个文件"**, 不是"最近 7 天"。停机三天后再跑, 这 7 个文件可能横跨十天。
3. **字符串排序 + 不补零的文件名** (`2026-10-9` vs `2026-10-10`) 会把日期排错, 归档可能挑走错误的文件。
4. **文件名日期取自宿主本地时区**, 与美国/UTC 时区的部署不符; 而日报一侧用的是中国时区, 午夜附近两者会错开一天。
5. **归档名带日期区间** (`-{first}-to-{last}.zip`), 同一区间重跑 (上次删除失败、恢复备份、文件重建) 会静默覆盖旧归档; 写 zip 与删源文件也不是原子的。

## 被放弃的方案与理由

- **继续用 ZIP / 按区间打包**: 单日无法独立还原, 需要整个区间一起解压; 区间命名天然会在重跑时覆盖; 还要继续依赖 `adm-zip` (它目前只为备份/恢复保留)。
- **保留 7 天且做成配置项**: 需求是"数据目录只允许两个日志文件"的硬约束; 增加 `FIELDS` 字段会同时扩大类型、清洗、双 WebUI 表单与文档面。
- **按文件数量保留 (保留最新 N 个)**: 与"天"脱钩, 停机或一天多分片时行为不可预测。
- **把存量 ZIP 迁移成 gzip**: 需要解压再重打包, 任何一步失败都可能损失历史; 旧归档原样保留的成本为零。
- **给归档加读取能力 (WebUI 下载 / 任意历史日期日报)**: 会引入解压、按需还原、缓存一致性等一整套问题, 而正常使用只需要今天与昨天。
- **把归档继续挂在轮询的跨天分支**: 归档与"是否成功启动轮询"无关, 不该由轮询的生命周期决定。

## 结论

- **保留窗口**: 数据目录只保留**今天与昨天**两个日志文件 (硬编码), 以中国时区的**日期键** `YYYY-MM-DD` 判定; 日期晚于今天的文件保留并告警。
- **归档格式**: 更早的日志逐日压缩为 `archives/steam-status-log-YYYY-MM-DD.json.gz`, 使用 Node 内置 `zlib`。写入顺序为"临时文件 → 回读校验 → rename 落位 → 删除源文件", 任一步失败都不删源。
- **同名冲突**: 解压比对, 内容一致只删源; 不一致另存 `-2`、`-3` 后缀, **永不覆盖**。
- **异常文件名**: 带日志前缀但解析不出日期的文件 (如 `steam-status-log-backup.json`) 原样 gzip 并保留原名, 数据目录保持干净且零丢失。
- **触发点**: 由 `timelineService` 自持的、墙钟对齐到 0/10/20/30/40/50 分的定时器驱动, 与轮询解耦; 插件启动时也执行一次 (合并同日命名 → 补启动快照 → 归档)。午夜快照同时移交该定时器, 时间戳固定为当日 00:00:00.000。
- **归日口径**: 日志按**事件时刻** (`detectedAt`) 的中国日期落盘; 跨天日报改为等待误报检测的待确认队列清空 (最多 `threshold + 1` 轮) 后再生成, 使晚确认的事件回到昨天。
- **只写不读**: 插件不读取归档; 1.3.0 及更早生成的 `.zip` 归档不迁移、不读取。
- **启动补点**: 只为今日日志中完全没有记录的缓存用户写一条起点记录, 时间戳为启动时刻 (近似值); 重启前的游玩时长无法还原, 不强行补成 00:00。
